## 问题17 MCP-01 HTTP MCP 携带 Origin 时响应格式错误

**处理结果：已修复。**

**原因**：`do_POST` 用 `_cors()` 判断来源是否允许，而 `_cors()` 在来源允许时会直接写入 CORS 响应头。这时状态行还没发出，CORS 头就排在了状态行前面；`_reply` 随后又把同一组头写了一遍。原始响应开头如下：

```
Access-Control-Allow-Origin: https://www.doubao.com
Vary: Origin
Access-Control-Expose-Headers: Mcp-Session-Id
HTTP/1.1 200 OK
```

**修改**（`studio_mcp_http.py`）：
- 新增 `_origin_ok()`，只负责判断来源，不写任何内容。
- `_cors()` 改为只写响应头，并且只在 `send_response()` 之后调用。

**自动回归**（`tests/test_mcp_http.py`，新增 2 项，用原始套接字读取响应头）：
- 允许的来源：第一行是 `HTTP/1.1 200`，每一行都是格式正确的响应头，`Access-Control-Allow-Origin` 和 `Vary` 各只出现一次。
- 拒绝的来源：返回 403，不带 `Access-Control-Allow-Origin`。
- 预检请求：允许的来源返回 204 并带 CORS 头；拒绝的来源返回 403。
- 原有的令牌、会话、Host 校验用例仍然通过。stdio 方式由 `test_studio_mcp`、`test_external_agents` 覆盖，也通过。

**剩余限制**：没有用豆包网页版做真实握手测试。

## 问题16 CLIENT-03 Hermes 配置编码损坏拖垮整个客户端列表

**处理结果：已修复。**

**原因**：读取 Hermes YAML 时直接按 UTF-8 解码，出错时抛出 `UnicodeDecodeError`。状态读取只捕获 `ClientError` 和 `OSError`，这个异常没有被接住，导致整个 `/api/studio/clients` 列表都报错。

**修改**（`studio_clients.py`）：
- 解码失败时转为明确、可修复的提示：“Hermes 配置文件不是 UTF-8 编码，原文件未改动。请用文本编辑器另存为 UTF-8 后点‘刷新’。”
- 客户端列表逐个读取，任何一个客户端读取失败，都只会把它自己显示为“需处理”，其他客户端照常显示。

**自动回归**：Hermes 配置写入非法 UTF-8 字节，同时保留一个已连接的 Claude Code：
- 客户端列表返回 200，Claude Code 仍显示“已连接”。
- Hermes 显示为 blocked，提示中包含 UTF-8。
- 尝试连接 Hermes 返回 409，原文件的字节没有任何改动。
- 设置页里 6 张客户端卡片全部显示。

## 问题15 CLIENT-02 客户端连接失败却已启用 MCP 总开关

**处理结果：已修复。**

**原因**：连接接口先打开 MCP 总开关，再写客户端配置。写配置失败时，开关已经打开了。

**修改**（`studio_control.py`）：先写客户端配置，写入成功后才打开开关。写入失败时，开关保持原来的状态。核实过：开关关闭时连接 Codex 也能成功，连接后开关会打开。

**自动回归**：
- 开关为关闭状态、Claude Code 配置文件是损坏的 JSON 时，连接返回 409；开关仍然关闭，原文件逐字节不变。
- 把配置修好后再连接，返回 200，开关打开。

## 问题14 CLIENT-01 Skill 入口丢失仍显示最新且安装跳过修复

**处理结果：已修复。**

**原因**：判断 Skill 状态、决定是否安装时只看版本标记文件。标记存在就算“最新”，即使 `SKILL.md` 已经被删除。

**修改**：
- `studio_clients.py` 新增 `_skill_health`：按标记里记录的文件清单和 sha256 逐个核对，结果分三种：
  - **damaged**：`SKILL.md` 或清单中的某个文件缺失，或清单路径不安全。
  - **modified**：文件内容与记录的哈希不一致。
  - **ok**：其余情况。
- 只有版本是最新、并且核对结果是 ok，安装时才会跳过；damaged 和 modified 会重新安装。旧文件夹照常先移到 `deepwhite-skill-backups/` 备份。
- 设置页（`studio-clients.js`）：
  - 新增两种状态标签：“文件缺失 · 需修复”“已被修改”。
  - 有 damaged 或 modified 的 Skill 时，按钮显示为“修复 Skills”。

**自动回归**：
- 删除 deepwhite-canvas 的 `SKILL.md`（保留版本标记）后，状态是 damaged。
- 改动 deepwhite-film 的 `SKILL.md` 后，状态是 modified；未动过的 deepwhite-avatar 仍是 latest。
- 再次安装只重装这两个；修复后入口文件存在，标记里记录的哈希与文件内容一致，三个 Skill 都是 latest。
- 在真实设置页中显示“文件缺失 · 需修复”，点击“修复 Skills”后恢复为“最新”。

**剩余限制**：用户自己改过的 Skill 会显示“已被修改”，点修复会恢复为官方版本，用户的版本保存在备份目录中。

## 问题21 CLIENT-04 相对 CODEX_HOME 可能让 Skill 装错目录

**处理结果：已修复。**

**原因**：两处对相对路径的处理不一致：
- Codex 配置部分拒绝相对路径，显示为“需处理”。
- Skill 安装部分直接使用相对路径，按当前工作目录写入。

所以 MCP 没有接上，Skill 却已经写进了一个意料之外的目录。

**修改**：
- `studio_codex_setup.py` 新增 `codex_home()`，作为 Codex 配置和 Codex Skills 共用的唯一目录解析：
  - 相对路径在第一次出现时，按画布服务的启动目录解析成绝对路径，之后固定不变。
  - 网络路径（UNC）仍然拒绝。
- 状态提示会写明“CODEX_HOME 是相对路径，已按画布的启动目录解析为 X；若 Codex 使用的不是这个目录，请把 CODEX_HOME 改为绝对路径。”
- 安装前，客户端卡片显示“Skills 位置：绝对路径”；安装完成的提示也写明“已安装最新 Skills 到 绝对路径”。

**这是一处约定变更**：原有用例 `test_codex_setup.test_broken_portable_launcher_and_relative_home_fail_safely` 要求相对路径显示为“需处理”。按交接报告的验收标准（解析为临时目录中的绝对路径，界面显示同一目标，只写入该目标），我修改了这条断言。用例现在核对三点：
- 配置路径是解析后的绝对目录。
- 提示中写明了这个目录。
- 读取状态时不创建任何文件。

原用例中“启动器损坏时显示需处理”的部分没有改动。

**自动回归**：在临时目录 work 下，把 `CODEX_HOME` 设为 `rel-codex`：
- 卡片显示的 Skills 位置和 Codex 配置路径都是 `work/rel-codex` 下的绝对路径。
- 安装提示中是同一个路径，文件只写到了那里。
- 之后切换工作目录，目标不会跟着变，也没有写到别的目录或默认的 `.codex`。

**剩余限制**：如果 Codex 自己从其他目录启动，它对相对 `CODEX_HOME` 的解析结果可能不同。界面已经提示建议改为绝对路径。
