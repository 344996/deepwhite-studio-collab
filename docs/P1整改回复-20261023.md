## 问题01 SAVE-01 智能画布冲突保存可能覆盖手写文字

**处理结果：已修复。**

**原因**：发生 409 冲突合并时，`mergeSmartNode` 以远端节点为底，只额外保护了 8 个草稿字段。提示词节点的正文保存在 `text` 字段，不在这 8 个字段里，所以会被远端的旧值覆盖；随后 300ms 的自动重试又把覆盖后的结果“保存成功”。

**修改**：
- 记录服务器最近一次确认过的节点状态，记录时机有三个：加载、保存成功、合并时。
- 合并改为三方比较，以这份确认状态为基准：
  - 只有本地改过的字段，保留本地值。
  - 只有外部改过的字段，采用外部值。
  - 两边都改了同一个节点内容字段（提示词正文 `text`、标题、分段符）时，保留本地值，并显示冲突提示条 `#studioSmartConflict`，列出具体节点和字段。此时自动保存暂停，保存结果报告 `conflict`，不会出现 `saved`。用户在提示条上选择“保留我的修改”或“采用外部版本”后再保存。
  - 两边都改了本页的输入框草稿（`promptDraftText`、`studioPrompt` 等）时，沿用原有约定，保留本页草稿，并提示“外部也改了输入框草稿，已保留本页草稿”。这一条由已有用例 `check-canvas-save-safety` 约定。
- 通过 WebSocket 或轮询收到外部更新时，合并走的是同一套逻辑。

**复现条件**（`tests/check-smart-save-merge.cjs`）：
- 使用真实的临时存储和真实页面。
- 先在本地改提示词正文，不保存。
- 再按当前版本号用 PUT 写入外部修改，与 MCP 或第二个窗口的写法相同，制造真实的 409。
- 修复前的结果：`UNSAVED USER TEXT` 变成 `original`，与交接证据一致。

**自动回归**：
- A：两边改的是不同字段，合并后都保留，重开画布后仍在。
- B：两边改了同一个字段，本地草稿保留，服务器上不会被悄悄覆盖；保存状态里没有 `ok`，只报告 `conflict`；选择“保留我的修改”后，保存的是本地版本。
- C：选择“采用外部版本”后，页面和服务器上都是外部版本。

**真实验证**：没有在两个真实窗口里人工复测。

**剩余限制**：
- 两边都改动的布局字段（坐标、尺寸）和运行状态字段，仍按“最新保存的一方”处理，不会弹出提示。
- 两边都改了输入框草稿时，外部那一份草稿会被本页草稿替换，只有提示，不需要选择。
- 冲突没处理之前，整张画布的自动保存都会暂停。
- 远端删除的节点仍可能“复活”，这是问题12，本次没有处理。

## 问题02 GROUP-01 智能分组复制后仍共享原成员

**处理结果：已修复。**

**原因**：复制只拷贝选中的节点。只选中分组时，副本的 `items` 仍然指向原来的成员 p1、p2，所以拖动副本会带着原成员一起移动。

**修改**：
- 新增 `smartCopySourceNodes`：复制分组时，递归收集分组的成员（包括嵌套分组）。
- 新增 `remapSmartCopyMembers`：把副本的 `items` 映射到新生成的 ID。
- Ctrl+C/V 和 Alt 拖拽复制两条路径都改了。

**复现条件**（`tests/check-smart-group-copy.cjs`）：
- 按报告的步骤操作：两个提示词按 Ctrl+G 成组，只选中分组，按 Ctrl+C、Ctrl+V，再用鼠标拖动副本。
- 修复前的结果：副本的 `items` 是 `["p1","p2"]`。

**自动回归**：
- 副本成员的 ID 与原组不同，而且都是真实存在的节点。
- 拖动副本后，原组和原成员的坐标不变，副本成员跟着副本移动。
- 编辑或删除副本成员，不影响原组。
- 撤销只恢复刚才的删除。
- 保存后在服务器上重新读取，结果一致。

**真实验证**：自动化测试使用真实浏览器和真实鼠标拖动，没有另做人工复测。

**剩余限制**：只修了智能画布；经典画布原本就会复制成员，没有改动。

## 问题03 RH-SMART-NATIVE-DURABILITY 智能画布 RH 应用/工作流绕过增强请求账本

**处理结果：已修复。全部为模拟验证，没有产生真实的 RH 提交或费用。**

**原因**：智能画布、级联运行和 MiniMax 都调用 `runRunningHubGeneration`。这个函数直接请求旧接口 `/api/runninghub/submit` 和 `/api/runninghub/workflow-submit`，请求里没有固定的请求编号。只要响应丢失，用户再点一次就会产生新的付费提交。

**修改**：
- 三个入口都改为提交到增强账本接口 `/api/studio/runninghub/tasks`。
- 提交前先生成 `request_id` 和提交快照，写入节点的 `studioRhRequest` 和 `studioRhSnapshot`，再用 `StudioSave.ensureCurrent` 保存画布并回读核对。核对通过后，才发出唯一一次提交 POST。
- 提交响应丢失时，先按原 `request_id` 查询账本：
  - 账本里查不到，说明请求没有登记，标为“未提交”。
  - 查得到，就继续查询这个原任务。
  - 账本本身也查询不了时，标为“待核实”。
- 同一个节点再次运行时，如果上一次请求还没结束，只查询原请求；如果原请求是“待核实”，会先弹窗说明可能已经产生费用，用户明确确认后才提交新任务。
- 查询改为调用账本的 `GET /api/studio/runninghub/tasks/{id}`。

**复现条件**（`tests/check-smart-rh-ledger.cjs` 和 `tests/rh-ledger-browser-server.py`）：
- 用假 RH 上游记录每一次提交，并真实重启服务进程，重启前后使用同一个数据目录。
- 情形 1：上游已经受理，但响应在返回浏览器途中丢失；随后服务重启，用户在同一个节点上重试。修复前上游被提交 2 次。
- 情形 2：上游已经受理，但它的回执没有到达账本。

**自动回归**：
- 情形 1：画布里保存的请求编号与提交时的请求编号一致；提交快照已经保存；重试后上游始终只被提交 1 次，并拿回同一个任务 `fake-task-1` 的结果。
- 情形 2：账本状态是“待核实”；重试不会再次提交，而是弹窗询问；用户拒绝时什么都不提交，只有明确确认后才提交一个新任务。
- 浏览器的提交请求全部经过账本接口，没有任何一次走旧接口。

**真实验证**：没有。交接报告说明原来的 RH 记录里没有出现真实的重复扣费。这次没有调用真实 RH，也没有产生费用。

**剩余限制**：
- RH 模型模式原本就走原生任务账本，这次没有改动。
- API 设置页的“测试运行”按钮仍直接调用旧接口，它不属于画布节点。
- 页面重新加载后不会自动轮询原任务，需要在同一个节点上再点一次运行，才会继续查询原请求。
- 问题06（素材没有上传到受管存储）、07（机器规格被丢弃）、08（种子精度损失）没有在这次处理。
