## 1. 产品概述

深白片场是面向 AI 影视创作的 Windows 独立桌面软件，核心工作区是可组织创作内容的无限画布。主创作链从剧本整理、拆解人物与场景，到制作并管理角色和场景资产。视频生成和音频创作（配音、音乐、音效）也纳入产品设计，按本轮已确认方案接入。

软件本身免费。用户可免登录使用本地画布和配置、测试自己的 API；调用深白 API 时按该服务规则收费，深白账号是按需使用。首页、注册和模型接入可参考 Fisher 的组织方式，但注册不能成为本地或自有 API 功能的前置条件。保留用户自有 API、即梦以及已有 ComfyUI 能力。每个生成节点分别选择渠道、模型和参数；创建新节点时记住默认选择，同一画布可混用不同渠道，不自动切换渠道。

独立工具工作台的产品拆分方式仍待后续评估。已有画布中的历史功能应纳入盘点和回归，明确区分“已实现”“模拟验证”“真实验证”，不把演示或模拟结果描述为真实可用能力。

已有视频生成、MJ 专项操作、图片处理、双图对比和视频截帧均纳入盘点与回归，发现问题需要修正。视频播放器支持截取帧作为创作素材。图片处理入口在重新设计期间先隐藏，保留兼容能力，不删除其实现或项目数据。双图对比是特殊功能节点，只能从专用工具入口创建，不出现在通用新增节点菜单中。聚焦角色、场景资产主链不代表删除这些已有能力。

## 2. 目标与设计原则

- 让创作者在同一项目中衔接剧本、资产方案、参考材料、生成任务和最终资产。
- 本地创作和自有渠道不以深白账号登录为前提；深白服务只在用户选择时调用。
- 每次生成都能追溯输入、渠道、模型、参数、任务状态和产物；不因失败而悄悄切换到其他收费渠道。
- 保存和恢复优先，关闭或重启软件后可继续查看项目及已提交任务。
- 先在现有画布基础上整理和验证，再依据基准测试决定是否替换画布引擎。
- 让版本、来源和复用关系清楚，删除画布内容不应意外删除仍被项目引用的正式资产。

## 3. 产品边界

| 主题 | 当前确认方向 |
|---|---|
| 平台与形态 | Windows 独立桌面软件 |
| 软件收费 | 软件免费；调用深白 API 收费 |
| 使用账号 | 本地功能与用户自有服务免登录；使用深白 API 时按服务要求连接账号 |
| 主创作链 | 剧本 → 角色／场景资产；视频与音频（配音、音乐、音效）纳入整体设计并分批接通，本轮按确认清单实施 |
| 服务接入 | 深白 API、自有 API、即梦、RunningHub API 和三种 ComfyUI 使用路径；具体能力需逐项验证 |
| 创作界面 | 无限画布为核心，保留既有功能并完成盘点与验证 |
| RH 工作流 | 通过 RunningHub API 使用在线服务，不将其工作流全量迁移为本地 ComfyUI 工作流 |
| ComfyUI | 支持预置扩展包、连接已有服务、自定义工作流转画布节点三种路径；连接测试与状态需可见 |
| Fisher 参考 | 已获作者授权，可直接复用其风格、MJ 码图和滤镜相关内容；不表示授权范围扩展到 Fisher 的所有数据或服务 |
| 工具产品 | 独立工具以后再评估；与画布的产品合并方式未定 |
| 本地数据 | 项目内容和媒体应能在本机保存并恢复；备份与迁移能力需在后续设计中落实 |

本版确认纳入视频生成及音频配音、音乐、音效的产品设计，实现与验证状态以当前验收表为准。尚未确认的能力不得以本设计文档推定为承诺，例如云同步、多人协作、移动端、具体订阅体系、完整模型目录或所有历史工具的发行范围。

## 4. 信息架构

建议的信息架构如下，视觉布局和具体交互先通过可点击 Demo 评审：

1. **首页／项目入口**：新建项目；按文件夹浏览、搜索和打开项目。
2. **项目画布**：放置剧本、人物／场景方案、参考素材、生成结果及其关系；执行核心创作操作。
3. **项目资产**：集中查看资产候选、已确认版本和来源，便于再次引用。
4. **任务记录**：查看运行中、成功、失败或待恢复的生成任务及其输出；余额按可用渠道分别展示，不把一个渠道的余额混为其他渠道余额。
5. **服务设置**：配置并测试自有 API，管理即梦、RunningHub API 及 ComfyUI 连接；按需连接深白 API，并清楚显示渠道、调用状态和可获得的余额信息。
6. **内容与工具**：风格、MJ 码图、滤镜等经授权内容；双图对比从专用工具入口创建。通用节点菜单不包含该特殊节点。图片处理暂隐藏入口并保留兼容。
7. **应用设置**：项目默认存储位置及桌面应用的基本设置；画布连线／流动方向设置放在基础设置中。其他选项待细化。

## 5. 核心创作流程

1. 用户新建或打开一个本地项目，进入无限画布；不导入剧本也可以自由创作。
2. 用户导入或粘贴剧本，保留原始文本，并可在画布中继续编辑。
3. 用户选择可用的分析能力，将剧本整理为人物、场景及其描述或提示词草案。
4. 用户检查并修改草案，再确认写入或更新画布中的对应内容。
5. 用户在每个生成节点分别选择渠道、模型和该渠道支持的参数，确认后提交生成任务；创建新节点时使用已记住的默认选择，同一画布内可以混用渠道。
6. 用户查看候选结果、比较版本，选择要保留或确认为正式使用的资产。
7. 用户可将确认资产再次引用到项目画布的其他创作内容中，并能追溯其来源和版本。

对剧本的再次拆解或修改应尽量保留可追踪关系和已有结果，具体的合并、冲突处理规则仍待需求文档确定。

## 6. 画布与资产设计

画布承载创作内容及其关联。节点关系应能表达参考或来源；连线本身不应被误解为自动执行生成。分组可通过框选内容创建；节点可按网格吸附和排列。文本输出节点应显示其使用或引用的提示词，便于检查内容来源。连线／流动方向在基础设置中配置。已有的平移、缩放、选择、移动、撤销重做、分组、媒体展示和其他工具能力先列入功能清单，逐项标注实现和验证状态，再决定保留、修复或移除。

资产至少区分“候选结果”和“已确认使用的版本”。生成新候选时保留此前版本，用户能看出版本对应的提示词、参考输入、模型／渠道和生成任务。一个资产被多个位置引用时，应能辨认各处使用的版本；移除画布引用与删除媒体文件应是不同且可理解的操作。细节以数据设计阶段为准。

双图对比作为专用工具创建的特殊节点，承载两张图像的并列或对比操作，不作为普通生成节点，也不混入通用新增节点菜单。其细节交互在可点击 Demo 中确认。

## 7. 工作流、模型与 ComfyUI

生成节点按“渠道 → 该渠道可用模型 → 该模型支持的参数”逐级配置。不同节点可独立选择渠道，因此同一画布可以混用深白 API、自有 API、即梦、RunningHub 和 ComfyUI。新建节点记住用户最近或已设定的默认项；渠道或模型不支持的参数不显示为可用项，渠道失败时不自动改用其他渠道。

RunningHub 工作流通过 RunningHub API 连接与调用，按服务开放能力呈现在线工作流，不要求把 RunningHub 全量内容和工作流搬成本地 ComfyUI 资产。在线工作流、模板定义和本地可执行工作流需区分展示；特定云端节点或服务依赖不得标成可本地运行。

ComfyUI 覆盖三种连接路径：

1. **预置扩展包**：用户选择整合包目录，进行连接/启动测试并显示运行状态；依用户设置按需启动。保持其现有环境，不自动更新扩展或下载模型。
2. **连接已有服务**：用户输入本地或可访问服务地址，执行连接测试，展示可达状态及可获得的版本、节点或能力信息；不要未经用户明确设置擅自启动或关闭外部服务。
3. **自定义工作流**：用户导入或选择 ComfyUI 工作流，将可配置的输入显式映射为画布节点参数。未暴露输入和依赖缺失需可辨认；不得把未安装节点、模型或云端专用能力伪装成本地可执行。

自动发现方式、连接测试覆盖范围、每种工作流可暴露的参数类型及依赖处理交互仍待细化。模型权重、自定义节点和工作流定义是不同的交付对象，提供目录或工作流模板不等于随应用交付了模型与运行依赖。

## 8. 任务状态与恢复

生成任务需要呈现用户能理解的生命周期：已提交、排队或运行中、成功、失败，以及提交结果暂时无法确认等状态。失败应提供可见原因或下一步信息；结果晚到时仍应归属到原项目和任务。

软件退出或重启后，应尽可能恢复任务记录并查询原任务状态，避免用户因界面关闭而不清楚任务是否仍在运行，也避免无提示地重复提交。若渠道不支持查询或恢复，应说明限制并保留可检查的任务记录。任务取消、重试和迟到结果的具体规则待接口盘点及后续细化。

## 9. Demo 与正式开发顺序

采用“讨论需求 → 制作可点击 Demo → 沿用旧版配色 → 用户确认布局、样式与交互 → 正式开发”的顺序。主题颜色集中配置，保留后续修改入口，不再等待额外美术参考。Demo 用于评审界面和交互，不代表模型接入、工作流、计费或生成链路已真实可用。正式功能须在最终样式与交互确认后开发；功能范围如有变化，再修订文档和版本记录。

Demo 优先覆盖首页项目文件夹浏览与搜索、画布节点及渠道选择、服务设置入口、ComfyUI 三种接入状态、内容／工具入口、双图对比专用入口、任务与按渠道余额展示。未接通的外部能力需用样例或明确状态呈现，不显示为真实成功。

## 10. 技术方向与演进约束

以下为当前方向，不构成已完成的技术实现或不可变的最终选型：

| 部分 | 当前方向 | 设计考虑 |
|---|---|---|
| Windows 桌面外壳 | Electron | 负责桌面窗口及与本地服务协作；安装、更新和服务生命周期须经原型验证 |
| 后台服务 | Python + FastAPI | 继续承载现有 Python 能力，复用经审查确认的渠道和素材逻辑 |
| 本地结构化数据 | SQLite | 管理项目、资产版本、关系和任务等结构化记录；媒体文件按文件保存 |
| 新增外围界面 | React + TypeScript + Vite | 逐步组织项目入口、资产区、任务区和设置等外围界面 |
| 现有画布 | 暂时保留现有实现 | 先建立代表性画布和操作基线，确保核心工作流及数据保存可回归 |
| 画布替换候选 | React Flow | 仅在基准测试、交互覆盖和迁移评估后决定是否替换；不预设必换 |

Electron、Python 后台和 React 界面通过明确的本地接口协作，生成及资产业务逻辑保持单一实现。新旧界面过渡期间应避免重复维护两套生成流程。迁移前需核对当前画布数据格式和历史项目兼容性。

## 11. 功能状态与验收

对每项既有或新增功能使用以下状态记录：

- **已实现**：代码中存在可交付实现；仍需注明测试覆盖情况。
- **模拟验证**：通过模拟数据、假服务或演示流程检查，未证明真实外部服务端到端可用。
- **真实验证**：使用目标渠道或实际 Windows 环境完成端到端检查，并记录验证条件。
- **未验证／未实现**：尚无足够证据证明可用，或尚未开发。

进入首阶段验收时至少满足：

- 在 Windows 桌面应用中能创建和重开本地项目，画布结构与素材引用得到保存。
- 从一份剧本完成拆解、人工检查、角色／场景候选生成、版本比较和资产确认的主链。
- 本地功能和自有 API 不依赖深白账号；选择深白 API 时可识别调用渠道、余额／计费归属和任务状态。
- 单个画布可混合使用多个生成渠道；每节点按渠道、模型及可用参数配置，新节点能使用已记住的默认选择。
- RunningHub 工作流按 API 在线调用；ComfyUI 预置扩展包、已有服务、自定义工作流三种路径均能显示连接测试结果和状态。
- 视频与配音、音乐、音效纳入分批实施与验收规划；各项接通状态如实标记，未完成项不宣称可用。
- 双图对比只能从专用入口创建；图片处理入口暂隐藏时，既有数据和兼容能力不受破坏。
- 任务失败、应用重启及结果延迟返回时，任务记录与项目归属明确，用户不会被误导为已成功。
- 既有功能清单标明实现状态及模拟／真实验证证据；未验证部分清楚标示。
- 若计划替换画布引擎，先用代表性项目比较主要操作、数据往返、性能和迁移代价，并记录结论。

验收样例、量化性能阈值、渠道覆盖矩阵、音视频接通批次和实际调用预算尚未确定，需经 Demo 评审与环境盘点后制定。

## 12. 已确认与待细化

**本次明确确认**

- 单节点配置渠道、模型、参数；默认选择可记忆；一个画布可混用渠道。
- RunningHub 通过 API 使用，不要求全量搬为本地工作流。
- 视频和音频（配音、音乐、音效）纳入设计，分批接通。
- 双图对比是专用入口创建的特殊节点；图片处理入口暂隐藏并保持兼容。
- Fisher 风格、MJ 码图、滤镜已获作者授权，可直接复制；Fisher 首页、注册和模型接入仅作交互参考，保留自有 API 管理与测试。
- 可点击 Demo 沿用旧版配色，用户确认布局、样式和操作后才进入正式功能开发。

**仍待细化**

- 首批音视频能力和分批接通顺序、逐渠道模型支持范围及余额查询能力。
