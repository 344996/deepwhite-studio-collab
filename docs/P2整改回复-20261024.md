## 问题06 RH-SMART-MANAGED-MEDIA 智能 RH 未上传受管存储路径

**处理结果：已修复。**

**原因**：智能画布只会上传 `http(s)`、`/output/`、`/assets/` 三类地址。`/input/...` 和 `/api/storage-files/...` 被当成普通文本，原样发给了 RH。上传接口没有返回 `fileName` 时，还会退回到发送本机路径。

**修改**：
- 可识别的受管路径与经典画布保持一致：`/output/`、`/assets/`、`/input/`、`/api/storage-files/`。本机媒体一律先上传，再用 RH 返回的 `fileName` 引用。
- 公网 URL 只在 URL 类字段（字段名含 `url`）里原样保留，其它媒体字段仍先上传。
- 上传失败或没有返回 `fileName` 时，报“素材上传失败（字段名）：原因，未提交。”，并阻止提交。这一步发生在登记请求和付费提交之前，不会生成任何请求记录。

**复现条件**：`check-smart-rh-params.cjs`，使用真实的上传接口和请求账本，加上假 RH 上游。修复前的情况：
- 本机路径被原样提交。
- 公网 URL 也被上传，下载失败后整个任务失败。
- 上传失败的素材仍被提交。

**自动回归**：
- `/input/` 和 `/api/storage-files/` 两个文件都已上传，并在请求中按 `fileName` 引用。
- 请求里没有任何本机路径。
- URL 字段中的公网地址没有改动，上游只收到 2 次上传。
- 素材不存在时，报出“素材上传失败”，没有提交，也没有生成请求记录。

**剩余限制**：
- 是否为 URL 字段按字段名判断（名称包含 url）。
- URL 字段遇到本机路径时仍会上传，并填入 `fileName`。
- 经典画布没有加 URL 字段规则，行为与修改前一致。

## 问题07 RH-SMART-INSTANCE-TYPE 智能工作流丢弃选定机器规格

**处理结果：已修复。**

**原因**：智能画布提交应用时会带上 `instanceType`，但组装工作流请求时漏了这个字段。后端工作流接口本身支持它。

**修改**：工作流请求也带上 `instanceType:runSettings.rhInstanceType || ''`。规格会随请求快照一起存进画布和请求账本。没有选择时为空，后端不发送这个字段，由 RH 使用默认规格（24G）。

**自动回归**：选择 plus 后，上游收到的工作流提交和画布里保存的请求快照都是 `instanceType=plus`。

**剩余限制**：没有启动真实的 RH 机器，所以没有核对 RH 实际分配的规格。

## 问题08 RH-SMART-SEED-PRECISION 长整数种子精度损失

**处理结果：已修复。**

**原因**：数值字段统一做了 `Number(value)`，超过 2^53 的整数会被舍入：`18446744073709551615` 变成了 `18446744073709552000`。工作流模式下，这个被舍入的值还会写进工作流 JSON。

**修改**：
- 前端新增 `rhExactNumberValue`：
  - 整数用 BigInt 和字段的 min/max 比较。超出范围时报“参数超出允许范围：字段名（最小值 ~ 最大值），当前值 X，未提交。”
  - `max ≤ min` 的范围视为占位值，不当作限制，这与滑块的处理方式相同。
  - 超出 JS 精确范围的整数保留为十进制字符串，RH 接受字符串形式的值；其余数值照常转为 Number。
- 后端 `sanitize_seed_like_workflow_values`：工作流 JSON 里，种子类字段的整数字符串会转成 Python int，保留每一位，JSON 中仍是整数。只转换直接写在字段上的值，`["5", 0]` 这类节点连线不受影响。

**自动回归**：
- 应用请求里的种子字符串逐字符不变。
- 请求快照里的种子也逐字符不变。
- 工作流 JSON 中写的是 `"seed": 18446744073709551615`。
- 字段上限为 4294967295 时，这个种子被明确拒绝，没有提交，也没有生成请求记录。

**剩余限制**：
- 随机种子仍由原有的随机函数生成，没有改动。
- API 设置页“测试运行”的旧入口没有修改。

## 问题12 SAVE-02 远端删除的节点或连线可能复活

**处理结果：已修复。**

**原因**：合并时，只在本页存在的节点一律保留（注释是“对方删了也宁可复活也不丢结果”），连线则取双方的并集。所以：
- 别处删掉的节点和连线，会被旧页面保存回来。
- 本页删掉的连线，也会在合并时被对方的副本带回来。

**修改**：沿用问题01的“服务器最近一次确认的版本”作为基准，这次把连线也记了进去。
- **对方删除、本页未改**：跟随删除。
- **本页删除、对方未改**：保持删除。
- **一方删除、另一方有修改**：先保留这个节点，提示条写明“外部已删除，本页有未保存修改”或“本页已删除，外部有新修改”。期间自动保存暂停。用户选择后，用正常的删除流程处理，连线、分组成员和撤销都会一起处理。
- **连线**：基准中有、而某一方已经删掉的连线不会被带回来。等待选择的节点，它的连线先保留。
- **“本页是否修改过”的判断**：只看内容字段（提示词正文、标题、分段符、输入框草稿、媒体）和是否正在生成；比较前先补齐渲染时会填入的默认值（分段符、模型等），`undefined`、`null`、`''` 视为相同。没有这一步，刚打开的页面会把未改动的节点误判为已修改。字段级合并使用同样的比较。

**复现条件**（`check-smart-remote-delete.cjs`）：
- 情形 A：报告中的场景。另一端删除 p2 及其连线，本页只改了 p3。
- 情形 B：本页删除一条连线，另一端改了其它内容。
- 情形 C：本页删除 r1，另一端修改了 r1；另一端删除 r2，本页修改了 r2。

修复前：A 的 p2 和连线都被带回来；B 的连线被带回来；C 不弹提示，直接把 r1、r2 都保存回去。

**自动回归**：
- A：p2 和连线保持删除，p3 的修改保留，重开画布后一致。
- B：连线保持删除，另一端的修改保留。
- C：服务器内容保持不变，弹出提示且没有出现“已保存”。选择“保留我的修改”后，r1 被删除，r2 带着本页的修改保存下来。

**剩余限制**：
- 判断“本页是否修改过”只看内容字段。只改了坐标或尺寸的节点，若被对方删除，会直接跟随删除，不会提示。
- 没有用两个真实窗口人工复测。
